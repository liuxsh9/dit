# 总体定位

针对大模型训练数据的 git

## 原始的用户痛点简述

我在公司负责大模型的后训练，目前一部分工作是管理代码类的 SFT 数据。目前我们的 SFT 采用两个阶段，第一阶段只训慢思考数据（有思维链），二阶段训慢思考+快思考数据。二阶段的慢思考数据，很大比例是从一阶段下采样过来的。虽然我管理这部分的数据，但是并不是只有我一个人生产。每周，很多位同事都会更新既有 SFT 数据。目前为了避免冲突，会分特性组，比如有 bug-fix 数据组，有 ascendc 数据组这样。组内，为了避免冲突，每个人会负责不同的数据文件。所谓数据文件，目前所有的 SFT 数据都是 jsonl 文件，每行是一条数据，每条数据格式类似于 openai fine tune 数据的 json 格式，再加上一些额外的元数据字段。所以目前就是通过这样的多个jsonl、多个文件夹，构成了 SFT 数据中的代码数据。代码数据每周会在贡献回全量的 SFT 数据集，每周替换掉或者说更新之前的文件夹。这些数据文件，则都存放在 S3 桶里。综上，整个数据管理的版本、更新过程，都非常的复杂。所以，关键问题是，有没有方案可以像 git 管理代码一样，有某个工具，或者值得构建这样一个工具，去管理 SFT 数据。额外补充的需求包括，目前会有一些数据标注流程，对每条数据打上更加细致的标签，目前打标完的详细数据，也是存在这些元数据里。另外，目前数据放入到文件夹前，还会跑一些格式检查，确保每行数据满足训练格式，没有一些关键词，没有不闭合等等。还有token统计工具。Anyway，以上环节都非常重要，但是目前都是完全松散的，管理记录全是靠 excel，有人更新了数据，没更新 excel，那我就要去擦屁股。另外，数据版本管理还有些非常独特的痛点，比如，删了几行，怎么识别到实际变更；有些数据 query 相同，response 是蒸馏的，蒸馏了多组，然而有可能会刷新教师模型时刷新一部分数据的 response，如何版本管理；有些元数据并不像写入到json里，比如数据构建流程、构建人，但是也要能跟着数据走；SFT数据有单轮数据也有多轮轨迹数据，这些数据的json格式会有区别，多轮轨迹数据里有工具有各种轮次，所以也得考虑，没有必要深入到一行内做过度的跟踪。综上，问题很复杂，请发挥你的专业能力，综合目前业界的既有工具和平台，给出 SFT 数据管理系统方案。如果没有既有系统能满足这些需求，那么请作为资深顶级架构师，LLM SFT 顶级训练专家，LLM 训练数据顶级专家，结合代码类数据规模（百万条、几十GB）以及可扩展性（全量数据几百万条），给出整套系统的架构设计，我们来实现一个真的系统，包括整套系统的端到端构成，哪些可以复用，哪些需要开发，最后是否能得到一个类似于 github 这样的现象级平台！

## 使用场景

pangu 整体的 SFT 代码数据，按照一个文件夹进行整理，主文件夹内，包含多个专项子文件夹，比如 feature implementation、general、
bug fix 等等，每个文件夹里，有若干个 jsonl 文件。每个 jsonl 文件的一行，为 json 格式，格式符合 panguml2.0 格式。ß

整个代码 SFT 数据就类似于一个项目，开发者可能负责不同的专项或者专项内的 jsonl。可能新增 jsonl、可能删除 jsonl、可能重命名。也非常可能对 jsonl 本身进行更新，比如原来有 10000 行，发现了一些问题之后，筛选到了 9500 行。

未来还会接入一些 CI/CD，比如用户每次合入时，比如新增文件或新增文件内的行时，会触发流水线（调用外部 API），直到流水线通过才能 merge。当然，因为 CI 会不断更新，老数据可能也会出问题，这个时候就会告知 CI 不通过，需要检查过滤等等，也支持直接抛弃掉未通过 CI 的数据。CI 这块目前不是开发重点，但供你思考系统全景。

## 难点

1. 新增或删除数据时，10000 -> 9500，如何精确的定位到，是哪 500 行被删了？我希望类似于 git，而不是像个二进制文件一样，一下次变更 9500 行这样，尤其是如果用户在一次提交里，新增了 500，删除了 1000，那看起来也是 9500，可是情况完全不同，甚至应该会触发 CI，以及用户在本地开发时，是否也有 git status，或者 git add 时的操作能感知到具体的变更？
2. 数据的一些元数据管理，本身 jsonl 的格式因为要用于训练，甚至提交到 pangu SFT 总数据（包括代码、数学、...），所以元数据不能随意写入到 jsonl 中（虽然 jsonl 里有一些 metadata 字段，但这些也是 pangu 统一定义的），如何参考 git 实现元数据的记录？
3. 数据集大小是挺庞大的，比如总量在 100GB 左右，所以肯定不太能像 git 那种，一下子直接下载整个代码仓（数据仓）下来，更多时候，可能最初都是 git clone 一个文件夹甚至一个文件，在修改后 add commit push 上去这样
4. 冲突处理，虽然因为大家一般各自负责文件，不会经常冲突，但有冲突时，如何优雅解决？
5. 代码数据集每个周需要出一个小版本，给到主线，同时可能发现小版本异常，就又会有修复版，再导出给主线等等，如何管理好？

## 数据结构

因为经常要对数据本身进行分析，所以 jsonl 的每行，并不希望真的视其为一个字符串，而是根据 json 格式能够进行展开和统计等等。因为用户在更新数据时，可能只是会更新 response，比如业界教师模型发生了刷新时，用户可能某一次提交，会针对这个 jsonl 进行回复刷新（也就是大多数 query 相同，也就是 role 为 user 的 content 是相同的，但 role 为 assistant 或者 tool 的 content 是不同的），但是文件数据量上也会有变化。这种更新的记录难度感觉很大，需要看看有什么方案

## 变更风险

目前数据是 pangu ml 2.0 格式，但说不好哪天，数据格式就变化了，这种时候，不希望对系统是一个毁灭性的打击

我们是否在构建一个在特定场景下，更为优化的 huggingface？

## 可扩展性

未来除了管理代码数据以外，可能也会有项目为数据数据，甚至到了最后，SFT 所有数据变成了一个大项目

## 终端体验

类似于 git 的表现，让熟悉 git 的用户，有自然而然的习惯来了咱们这个数据 git 的一些操作，同时，具备尽可能想管理代码的能力来管理数据

## 前端体验

github 或者 huggingface 二选一，因为有数据的审核过程，包括需要比较完备的权限管理，比如 reviewer、committer，针对不同 branch 有不同的权限等，所以我觉得，会更像 github？如果你也觉得 github 合适，那么所有的设计，应该都按照 github 来，当然，gitlab 也完全可以，用 gitlab 可以复用很多的前端代码我觉得，毕竟是开源项目

## 设计原则

考虑 dolt 可否作为最基础的依赖？
dolt 相关的前端项目是否有较为成熟的？

可以考虑多个项目的结合，避免从 0 开始
